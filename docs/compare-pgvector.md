# SQL Server 2025 / Azure SQL vs PostgreSQL + pgvector

If you already know pgvector, this is the cheat sheet. If you know SQL
Server, read it the other way round. The left column is what this repo
runs; the right column is the equivalent in the sibling Postgres project
([azure-data-pg-rag](https://github.com/sharath568/azure-data-pg-rag)).

Print it in a terminal with `sqlvec compare-pg` (or `--format markdown`).
The table below is generated from `src/sqlvec/compare.py`, and a unit test
fails if the two drift apart.

Status notes reflect Microsoft Learn as of October 2026. Details and links are
in [sources.md](sources.md).

## The differences that actually matter

**Approximate is explicit in T-SQL.** In Postgres the same `ORDER BY
embedding <=> :qv LIMIT 10` is exact without an index and approximate with
one, and the planner picks. In SQL Server, `VECTOR_DISTANCE` is always exact
and you opt into the index with `VECTOR_SEARCH` and `TOP (n) WITH
APPROXIMATE`. I like that: you can read the query and know what you get.

**There is only one ANN index type and no knob.** DiskANN, cosine / dot /
euclidean. pgvector gives you HNSW and IVFFlat with `ef_search`,
`ef_construction`, `m`, `lists`, `probes`. Fewer knobs means less to get
wrong, but also no way to trade recall for latency at query time.

**On boxed SQL Server 2025 the index is still preview.** Vectors and
`VECTOR_DISTANCE` are GA everywhere. `CREATE VECTOR INDEX` / `VECTOR_SEARCH`
are GA in Azure SQL Database, Fabric and Managed Instance (Always-up-to-date
policy), but preview in SQL Server 2025, behind
`ALTER DATABASE SCOPED CONFIGURATION SET PREVIEW_FEATURES = ON`.

**The table and the index have rules.** DiskANN needs an `INT` clustered
primary key and at least 100 rows. No `TRUNCATE` while it exists. Earlier
index versions made the table read-only; the current version allows normal
DML. pgvector has none of these constraints.

**Dimensions.** float32 `VECTOR` tops out at 1,998 dimensions (3,996 for
float16). `text-embedding-3-large` (3,072) needs float16, or ask the model
for fewer dimensions. pgvector's `vector` stores up to 16,000 but only
indexes 2,000 (4,000 with `halfvec`).

**Full-text is a separate install on Linux.** Postgres has `tsvector` built
in. SQL Server's full-text engine is `mssql-server-fts` on Linux and isn't
in the official container image. Azure SQL Database has it built in.

**Metadata filters.** `jsonb @> ...` with a GIN index is hard to beat. In
T-SQL you either check JSON per row (what sqlvec does, via `OPENJSON`) or
promote hot keys to real columns or computed columns and index those. For a
DBA that second option is the obvious one; do it for any filter you use a lot.
